**截至 2026 年 8 月，这个 `node-modules/.pnpm/...`路径写死进 mp 产物的问题，在 `@dcloudio/vite-plugin-uni`主线里并没有一个"已关闭修复"的官方定论。** 准确说分几层：

## 官方态度与现状

- 

  DCloud 官方文档里，**uni-ui 通过 npm 安装后的标准用法**仍然是 `pages.json`里配 `"^uni-(.*)": "@dcloudio/uni-ui/lib/uni-$1/uni-$1.vue"`，官方 quickstart 文档没提 pnpm 下会写出 `node-modules`连字符路径。

- 

  但官方同时把 **`uni_modules/`目录规范**定义为 uni-app 插件/组件的首选承载方式（即放项目里、不进 node_modules），相当于官方预留的"正统绕开方案"。

- 

  社区里（CSDN/AtomGit 等）大量 2025–2026 年的帖子仍在报 `Component is not found in path "node-modules/@dcloudio/uni-ui/..."`这个**完全相同**的现象，说明主线版本（你用的 uni-ui 1.5.12 + vite-plugin-uni 对应版本）**并没有在编译器层把 pnpm virtual store 路径生成逻辑改对**。

- 

  已知相关兼容问题（如 pnpm 下 `@dcloudio/uni-cli-shared`解析失败、Rollup 4 tree-shaking 白屏）官方/社区是用 `overrides`、`public-hoist-pattern`、`shamefully-hoist`这类**绕过手段**解决的，不是编译器自己修对了。

## 为什么它"不算 bug 但就是不好用"

严格讲 DCloud 可以说"我们用 HBuilderX + uni_modules 体系是支持的，pnpm 硬链接/symlink 场景不在首选支持矩阵内"——也就是：

- 

  **npm/yarn 常规装** → 多数情况 easycom 指向 `@dcloudio/uni-ui/lib/...`能跑（因为 node_modules 是平铺的）

- 

  **pnpm 严格模式** → virtual store 在 `.pnpm/`，编译器生成 `usingComponents`路径时跟 symlink 跟出内部串，写出 `node-modules`（连字符是 pnpm 内部目录名被原样拼接），微信不认

- 

  官方没在 `vite-plugin-uni`的 mp 产物生成阶段做"pnpm 感知+路径归一化"

所以它不是 GitHub 上一个标着 `fixed in 3.x.x`的清晰 bug，而是**"pnpm 非 hoisted 模式 + vite-plugin-uni 小程序产物"的组合缺陷**，长期存在、靠 workaround 活着。

## 对你而言的结论

- 

  升最新 `@dcloudio/vite-plugin-uni`+ `@dcloudio/uni-ui@latest`**可能**缓解，但**不保证**把你这个 1.5.12 场景的 `node-modules`连字符彻底消掉（社区有人升了还踩）。

- 

  官方"正路"其实两条：

  1. 

     用 HBuilderX 从插件市场装 uni-ui → 进 `uni_modules/`（你现在走的）

  2. 

     或者 pnpm 下接受 `shamefully-hoist=true`把 node_modules 拍平，赌编译器能解析对

- 

  你选的 `uni_modules/`拷贝方案，**和 DCloud 官方推荐的 uni_modules 规范是一致的**，不是野路子。

> 简单说：没"修好"，官方当已知限制处理，建议你别等修复——`uni_modules/`方案就是官方体系内最稳的答案。

要不要我帮你把 `package.json`里加个 `pnpm.overrides`锁一下 `@dcloudio/vite-plugin-uni`和 `uni-ui`到最新试跑一次，验证下你这个特定版本升了会不会变？变了你就省掉拷贝，没变就继续用 `uni_modules/`。
