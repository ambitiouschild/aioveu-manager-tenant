不是你代码退步了，是**环境变了，easycom 在「分包 + npm 版 uni-ui + 微信小程序」这个组合下的行为被悄悄改掉了**。早先能跑，是几个条件刚好同时成立；现在其中一个变了，就断了。

## 以前为什么能跑

早些版本的 uni-app（Vue2 时代 / 早期 Vue3+HBuilderX 内置编译器）里，easycom 的扫描和注入比较“粗”：

- 

  主包页面用 `<uni-popup>`→ easycom 注入 → 没问题

- 

  **分包页面用 `<uni-popup>`** → 老编译器在生成 `packageX/xxx.json`的 `usingComponents`时，也会把 `node-modules/@dcloudio/uni-ui/lib/uni-popup/uni-popup`写进去

- 

  微信小程序运行时，分包页面反向引用这个 npm 映射路径，居然能解析到（HBuilderX 把 npm 包预处理成 `node-modules/`时顺手打通了）

所以你“以前不拷贝、不 import、光靠 easycom 在分包里也能用 uni-popup”是真的，不是错觉。

## 现在为什么断了

后面这几件事任意踩中一个，老办法就不灵：

1. 

   **@dcloudio/uni-ui 包结构变过**

   1.4.29 左右把组件从 `lib/uni-xxx/uni-xxx.vue`挪过位置，老 easycom 正则 `@dcloudio/uni-ui/lib/uni-$1/uni-$1.vue`直接匹配不到，必须改规则。很多人就是升级 uni-ui 后突然挂的。

2. 

   **@dcloudio/vite-plugin-uni / HBuilderX 编译器升级**

   Vue3+Vite 路线下，easycom 对**分包页面**的 `usingComponents`注入变得更“守规矩”——小程序原生要求分包组件要么在分包内、要么显式声明，编译器不再替你跨包注入 npm 路径。于是编译产物里分包 json 没写 uni-popup → 运行时报 `node-modules/@dcloudio/uni-ui/lib/uni-transition/... not found`。

3. 

   **cli 项目默认不编译 node_modules**

   Vue3 cli 工程里 `transpileDependencies`没加 `@dcloudio/uni-ui`时，条件编译失效、组件解析异常，easycom 扫描也会出怪事。

4. 

   **你这个 CategoryTree 是显式 import 本地副本**

   一旦你手动 `import uniPopup from "@/packageC/components/uni-popup/uni-popup.vue"`，easycom 就**完全不接管**这个组件及其子组件（uni-transition/uni-icons），子组件必须自己闭包解决——这跟你“以前页面里直接写 `<uni-popup>`靠 easycom”不是同一条路径。

> 简单说：**以前是编译器帮你“违规”跨包注入成功了；现在编译器按小程序原生规则收严了，违规路径不再兜底。**

## 为什么“放进分包”反而成了最稳的

因为微信小程序原生规则本来就是：

- 

  分包页面用组件 → 组件得在分包内，或主包显式声明

- 

  easycom 只是编译期语法糖，不颠覆小程序原生加载模型

所以你现在做的「uni-popup + uni-transition + uni-icons 整体抄进 `packageC/components/`+ 显式 import 注册」反而是**贴合小程序原生模型**的写法，不依赖编译器兜底，升级编译器也不会再突然崩。

## 一句话收尾

> 老早能跑 = 老编译器替你跨包注入 npm 路径成功了；
>
> 现在不行 = 编译器升级/uni-ui 改结构/easycom 不兜底分包子组件，三条任意一条都能让老办法断；
>
> 把 uni-ui 相关组件闭包进分包 = 回到小程序原生能解释的模式，所以现阶段确实最稳。

要是哪天你想验证是不是“编译器升级”背锅，最简单：把 `@dcloudio/vite-plugin-uni`和 `@dcloudio/uni-ui`版本号跟 `package-lock`里几个月前能跑的版本对齐，重装编译，大概率又能靠 easycom 跑——但没必要回去了，分包闭包更可控。
